# Restate v1.7.13 Release Notes

## Highlights

- **Consistent state changes across replicas**: With vqueues enabled, Virtual Object state changes made through the Admin API are now applied on all partition replicas.
- **Graceful HTTP/2 GOAWAY handling**: A GOAWAY from a service endpoint no longer interrupts unrelated in-flight invocations.
- **Configurable RocksDB write rate limiter**: A new `rocksdb-write-rate-limiter-mode` option disables the rate limiter's slow ramp-up for bursty write loads.

## New Features

### Configurable RocksDB Write Rate Limiter Mode

A new option, `rocksdb-write-rate-limiter-mode`, controls how `rocksdb-max-write-rate-per-second` is applied to RocksDB flushes and compactions:

- `auto-tuned` (default, unchanged behavior): the write rate adapts to recent demand, starting as low as 1/20 of the configured maximum and taking minutes to ramp up. A sudden write burst can therefore stall until the rate has climbed.
- `fixed`: the full configured maximum is available immediately, with no ramp-up.

Existing deployments are unaffected. If you see write stalls under bursty load, set the mode together with a maximum your storage device can sustain, and restart the node:

```toml
rocksdb-max-write-rate-per-second = "2400 MiB"
rocksdb-write-rate-limiter-mode = "fixed"
```

_Related: [#5408](https://github.com/restatedev/restate/pull/5408)_

## Bug Fixes

### State Changes via the Admin API Applied on All Replicas

With vqueues enabled, changing the state of a Virtual Object through the Admin API (`POST /services/{service}/state`, e.g. `restate state edit|patch|clear`) could leave the replicas of a partition with different state: the change was applied on the leader but might be skipped by the followers. After a leader change, the Virtual Object could then continue with its old state. State changes are now applied on all replicas.

**Impact on users:**

- Only clusters with a replication factor greater than 1 that used the state API while vqueues were enabled are affected.
- If this applies to you, re-submit the state of the affected Virtual Objects after upgrading (e.g. with `restate state edit`) to bring all replicas back in line.

_Related: [#5416](https://github.com/restatedev/restate/issues/5416)_

### Preserve Active HTTP/2 Streams During Graceful GOAWAY

When a service endpoint sent a graceful GOAWAY on an HTTP/2 connection, Restate could cancel the connection and interrupt unrelated service invocations in progress on it. The connection is now drained gracefully: in-flight invocations complete, and new requests are retried on another connection.

No configuration or migration is required.

_Related: [#5311](https://github.com/restatedev/restate/pull/5311)_
