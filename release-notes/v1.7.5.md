# Restate v1.7.5 Release Notes

## Highlights

- **HTTP/2 security and workload protection**: Updated HTTP/2 dependencies address excessive memory use from empty DATA frames, while a new configurable frame budget supports legitimate workloads that send many small frames.
- **Safer VQueue migrations**: Operators can skip completed invocations during migration, with the partial migration state persisted so the remaining entries can be migrated later.
- **Expanded VQueue observability in the UI**: The bundled Restate UI adds VQueue, flow-control, rule, Virtual Object, and Workflow views.

## New Features

### Skip Completed Invocations During VQueue Migration

VQueue migrations can now skip completed invocations. This can significantly reduce migration time for partition stores with a large completion-retention backlog:

```toml
experimental_enable_vqueues = true
experimental_enable_vqueues_migration_skip_completed = true
```

Completed invocations retain their existing status and continue to be removed by their cleanup timers, but they do not appear in VQueue introspection after a skip-completed migration.

Restate now records the partial migration as a persisted partition feature. If `experimental_enable_vqueues_migration_skip_completed` is later set to `false`, Restate migrates the remaining completed invocations and marks the partition as fully migrated. If the initial scan finds no completed invocations to skip, the partition is marked fully migrated immediately.

All nodes must be upgraded to v1.7.5 before enabling this option because the persisted partition feature requires v1.7.5 or later. The option requires VQueues to be enabled.

_Related: [#5210](https://github.com/restatedev/restate/pull/5210), [#5211](https://github.com/restatedev/restate/pull/5211)_

## Improvements

### HTTP/2 DATA Frame Budget

Outbound service connections now use a connection-level budget for HTTP/2 DATA framing overhead. This protects Restate from disproportionate memory use while allowing legitimate service workloads that fragment payloads into many small frames.

The budget defaults to 1 MiB. Workloads that exhaust it receive an actionable error and can increase it with:

```toml
[worker.invoker]
http2-data-frame-budget = "2 MiB"
```

Values below 25,600 bytes are raised to 25,600 bytes. Most deployments do not need to change the default.

_Related: [#5209](https://github.com/restatedev/restate/pull/5209), [hyperium/h2#942](https://github.com/hyperium/h2/pull/942)_

### Partition-Store Compaction Configuration

The maximum number of RocksDB subcompactions for each partition store is now configurable:

```toml
[worker.storage]
rocksdb-max-sub-compactions = 4
```

The default is `1`, which disables subcompactions. A configured value of `0` is also treated as `1`.

### Restate UI 1.0.18

The bundled Restate UI is updated to **v1.0.18**. It adds dedicated views for Virtual Objects, Workflows, VQueues, flow-control rules, and invocation statistics, together with navigation and filtering improvements. It also fixes the transient-error selection control.

_Related: [Restate UI v1.0.18](https://github.com/restatedev/restate-web-ui/releases/tag/v1.0.18), [#5190](https://github.com/restatedev/restate/pull/5190)_

## Stability and Security

### HTTP/2 Dependency Security Update

The `h2` and `hyper` dependencies have been updated to address [RUSTSEC-2026-0258](https://rustsec.org/advisories/RUSTSEC-2026-0258.html), in which a peer could cause excessive memory use or a panic by sending a large number of empty HTTP/2 DATA frames.

No configuration changes are required. The HTTP/2 DATA frame budget described above provides an adjustable limit for service workloads that legitimately send many small, non-empty frames.

_Related: [#5188](https://github.com/restatedev/restate/pull/5188)_

## Bug Fixes

### Drain Partition-Store Opens Before Cancellation

Fixed a race between partition-processor cancellation and opening its RocksDB partition store. RocksDB open operations continue on the storage pool if their awaiting future is dropped; a replacement processor could therefore start while an abandoned open was still completing, causing database lock errors or shutdown crashes.

Once a partition-store open begins, Restate now waits for it to complete before honoring processor cancellation. The restart delay before the open remains cancellable.

No configuration or migration changes are required.

_Related: [#4790](https://github.com/restatedev/restate/issues/4790), [#5191](https://github.com/restatedev/restate/pull/5191)_

### Apply Compaction Limits to Column Families

The relaxed pending-compaction limits announced in v1.7.4 are now applied to each partition-store column family, where RocksDB enforces them. This corrects an oversight that could still cause partition-store writes to slow or stop when compaction fell behind.

The soft limit is 512 GiB and the hard limit is 2 TiB. These limits favor continued writes and flushes at the cost of potentially higher temporary disk usage while compaction debt remains high.

No configuration or migration changes are required.

_Related: [#5205](https://github.com/restatedev/restate/pull/5205)_
