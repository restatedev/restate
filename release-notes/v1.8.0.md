# Restate v1.8.0 Release Notes

## Highlights

- **VQueues are on by default**: Virtual queues no longer need an opt-in.

- **A CLI built for scripts, CI and AI agents**: `restate --json` prints one parseable JSON document, failures come with structured error objects and distinct exit codes, and state-changing commands share a `--dry-run` / `--yes` preview-then-apply flow. New `invocations journal`, `sql describe` and `search` commands make inspection easier for humans too.

- **Google Cloud Storage for cluster metadata**: The object-store metadata backend now accepts `gs://` paths, so clusters on Google Cloud can keep their metadata in a GCS bucket.

- **Service protocol v7 is the default and v3 and older are gone**: Deployments still on service protocol v3 or older must upgrade their SDK before upgrading the server.

## Upgrade Guidance

Read this section before upgrading a cluster.

### Before upgrading

1. **All nodes must run v1.7.3 or newer, ideally the latest patch release.** The VQueues migration requires v1.7.3 or newer on every node. Clusters on v1.6 or older must first upgrade to the latest v1.7.x and come up healthy, then upgrade to v1.8.0.
2. **Check for invocations pinned to service protocol v3 or older** and drain them or upgrade the SDK before upgrading (see [below](#service-protocol-v3-and-older-no-longer-supported)).
3. **Review `worker.invoker.concurrent-invocations-limit`** if you set it explicitly. Once upgraded, it applies per node instead of per partition (see [below](#invoker-concurrency-limit-is-now-per-node)).
4. **Remove `SET` statements from SQL scripts and dashboards** that query Restate; they are rejected after the upgrade (see [below](#sql-set-statements-rejected)).

### After upgrading

1. **Remove obsolete configuration**: the `experimental-enable-vqueues`, `experimental-enable-vqueues-migration-skip-completed`, `experimental-enable-invoker-yield`, `experimental-enable-scoped-virtual-objects`, `experimental-enable-protocol-v7` and `experimental-enable-unique-random-seeds` flags, the `worker.invoker.tmp-dir` and `worker.invoker.in-memory-queue-length-limit` options, and the `tracing-runtime-endpoint`, `tracing-json-path` and `tracing-filter` options no longer have any effect.
2. **Rolling back to v1.7** (v1.7.3 or newer) remains possible unless you enable one of the experimental features that are marked as one-way below. Rolled-back nodes must run with `experimental-enable-vqueues = true` (plus `experimental-enable-scoped-virtual-objects = true` and `experimental-enable-invoker-yield = true` if you rely on those behaviors), otherwise they reject scoped invocations and fall back to per-partition concurrency limits.

## Breaking Changes

### Service Protocol v3 and Older No Longer Supported

Restate no longer runs invocations against deployments using service protocol v3 or older. Such invocations fail immediately with `RT0020` (`service <name> is exposed by the deprecated deployment <id>, please upgrade the SDK used by the service`) instead of retrying.

**Before upgrading**, check whether any invocations are still pinned to an old protocol version:

```sql
SELECT id, target, pinned_deployment_id, pinned_service_protocol_version
FROM sys_invocation_status
WHERE pinned_service_protocol_version <= 3;
```

The column is only set once an invocation has started, so invocations that have not started yet do not appear. If the query returns rows, let those invocations complete or terminate them.

**After upgrading**, invocations that failed with `RT0020` can be re-run from scratch with restart-as-new. The new invocation records the original one in the `restarted_from` column of `sys_invocation_status`.

### VQueues Enabled by Default

Virtual queues (VQueues) and the features built on them are now always on. The `experimental-enable-vqueues`, `experimental-enable-vqueues-migration-skip-completed`, `experimental-enable-invoker-yield` and `experimental-enable-scoped-virtual-objects` flags have been removed and no longer have any effect.

**What this means for you:**

- On upgrade, each partition that has not yet migrated to VQueues migrates when its leader is elected. The migration includes completed invocations, so partitions with a large completion-retention backlog take longer. The migration is **one-way**; v1.7.3 and newer can still operate migrated partitions.
- Invocations that exhaust the invoker memory pool now yield back to the scheduler instead of consuming retry attempts.
- Scoped invocations, including scoped Virtual Object targets, are accepted without opt-in. During a rolling upgrade, scoped requests reaching a partition that has not migrated yet run without scope-based concurrency limits, so start using scopes only after the whole cluster runs v1.8.
- Pausing an in-flight invocation through the Admin API now aborts the running attempt immediately instead of waiting for a suspension point. A `ctx.run` closure that already started keeps running inside the SDK, but its result cannot be recorded, so it re-executes on resume. A graceful pause variant is planned ([#5321](https://github.com/restatedev/restate/issues/5321)).

**Reducing migration time for very large invocation histories** (as a guideline, partitions holding more than 10 million invocations): first upgrade to v1.7.11 or newer with `experimental-enable-vqueues = true` and `experimental-enable-vqueues-migration-skip-completed = true`, so only running invocations are migrated. Once the completed backlog has fallen out of retention, upgrading to v1.8 completes the migration with little remaining work.

### Invoker Concurrency Limit Is Now Per Node

`worker.invoker.concurrent-invocations-limit` now caps the whole node instead of each partition processor, and its default has increased from `1000` to `24000`.

- **Using the default**: a node now runs up to 24000 concurrent invocations regardless of how many partitions it hosts. Verify your services and their downstream dependencies can handle this.
- **Explicit value**: your value is kept but now applies to the node. A value tuned per partition is likely too low; as a starting point, multiply it by the number of partitions a node typically hosts.

```toml
[worker.invoker]
concurrent-invocations-limit = 24000
```

### `sys_keyed_service_status` Table Removed

The `sys_keyed_service_status` SQL table has been replaced by `sys_locks`. Queries against the old table fail with a "table not found" error.

| `sys_keyed_service_status`    | `sys_locks`                                                  |
|-------------------------------|--------------------------------------------------------------|
| `service_name`, `service_key` | `lock_name` (formatted as `service/key`); `scope` for scoped Virtual Objects |
| `invocation_id`               | `acquired_by`                                                |
| —                             | `acquired_at` (new)                                          |

```sql
-- Old
SELECT service_name, service_key, invocation_id FROM sys_keyed_service_status;
-- New
SELECT scope, lock_name, acquired_by, acquired_at FROM sys_locks;
```

### `/cluster-health` Endpoint Removed

The Admin API endpoint `/cluster-health`, deprecated in v1.6.0, now returns `404 Not Found`. Update probes and scripts to use `GET http://localhost:9070/health` (Admin API) or `GET http://localhost:8080/restate/health` (ingress), and `restatectl status` to inspect the cluster.

### Ingress Drops Client-Supplied `x-restate-*` Headers

The `x-restate-*` header namespace is reserved for the ingress. Client-supplied headers with this prefix are now dropped before the request reaches your service, so they can no longer spoof or override ingress metadata such as `x-restate-ingress-path`. If you forwarded custom metadata through such headers, rename them to a prefix that does not start with `x-restate-`.

### Runtime Tracing Options Removed

The inactive runtime trace exporter and its options `tracing-runtime-endpoint`, `tracing-json-path` and `tracing-filter` have been removed. Remove them from your configuration. The matching command-line flags are still accepted, have no effect, print a deprecation warning, and will be removed in v1.9.0.

Tracing of your invocations is unaffected and keeps using `tracing-services-endpoint`, or `tracing-endpoint` as its fallback.

### SQL `SET` Statements Rejected

The SQL introspection interface (the Admin API's `/query` endpoint, `restate sql` and the UI) no longer accepts `SET` and `RESET` statements, nor transaction, `PREPARE`, `EXECUTE` and `DEALLOCATE` statements. They fail with `Statement not supported`. `SELECT`, `EXPLAIN` and `SHOW` are unaffected.

All SQL requests share one query engine, so a `SET` issued by one client silently changed the settings for every other client until the next restart. Remove such statements from scripts and dashboards; engine settings that should apply to all queries belong in the server configuration under `admin.query-engine.datafusion-options`.

### CLI Behavior Changes

The `restate` CLI's human-readable output was redesigned; scripts should use `--json` instead of parsing it. In addition:

- `restate deployments register` requires Restate server v1.6 or newer.
- In non-interactive mode, a refused confirmation now exits with code `3` (confirmation required) instead of `7`.
- `restate invocations describe` shows a journal preview instead of the full call graph; use the new `restate invocations journal <id>` for the full journal.
- `restate sql describe --json` output is wrapped in an object (`{"table": {...}, "columns": [...]}`).
- Bulk `restate invocations` commands and `restate state clear` whose query matches nothing now succeed with exit code `0` (with `--json`, an empty `changes` array and `"result": "nothing_to_do"`) instead of failing with exit code `1`.
- `--yes` never waits for input: a command that would ask you to pick or type a value fails and asks for it as an argument instead, or uses its default.
- The `CI` environment variable only implies `--yes` when set to a truthy value; empty, `false` and `0` now count as unset.

## New Features

### CLI Revamp

The `restate` CLI is now first-class for scripting, CI and AI agents while staying friendly for humans.

**Structured output.** A global `--json` flag prints a single JSON document on stdout; diagnostics go to stderr. It is supported by `services list|describe|status|config view`, `deployments list|describe`, `invocations list|describe|journal`, `state get`, `vqueues list|describe`, `rules list|set|enable|disable|delete`, `whoami`, `sql describe` and `config view`. Timestamps are always RFC 3339, service types use one vocabulary (`service`, `virtual_object`, `workflow`), and collections are ordered deterministically. Where a read-only follow-up is useful, the document carries a `next_steps` array with ready-to-run commands; human output shows the same as a tip.

**Machine-readable errors and exit codes.** With `--json`, failures print `{"error": {"kind": "...", "message": "...", "causes": [...], "docs_url": "...", "next_steps": [...]}}` (the last three only when present) and exit with a distinct code: `2` invalid usage, `3` confirmation required, `4` not found, `5` network, `6` auth, `7` aborted, `8` server error, `1` other. For a server error, `message` is the server's own text followed by the HTTP status and URL. Errors with a Restate error code link to its documentation, and suggest read-only next steps (`whoami` on connection failures, the matching `list` on not found). `whoami` exits non-zero when the server is unhealthy, and `state get` exits `4` when there is no state.

**Preview and confirm changes.** All state-changing commands (`deployments register|remove`, `invocations cancel|kill|purge|pause|resume|restart-as-new`, `state clear|patch`, `services config patch`, `rules delete`) share one flow: `--dry-run` shows the plan and applies nothing; `--json` without `--yes` prints the plan (with a ready-to-run `apply_command`) and exits `3`; `--yes` applies and reports per-item results for bulk operations. Interactive runs still preview and prompt. `CI=true` counts as `--yes`; use `--dry-run` in CI to only preview.

**New global flags.** `--color <auto|always|never>` and `--non-interactive` (implied by `--json`, a non-terminal stdin, or `CI`). Editor-based commands fail in non-interactive mode and point to the matching `patch` command.

**Inspecting journals.** `restate invocations journal <id>` shows a head-and-tail preview by default, supports index ranges (`5`, `1..3`, `..10`, `90..`, `--all`), and decodes payloads with `--payload`. Combine with `--json` to pipe into `jq`. Invocations that are retrying are now reported as `backing-off` with retry count, next retry and last failure, and can be filtered with `invocations list --status backing-off`.

**SQL schema at your fingertips.** `restate sql describe <table>` prints a table's columns with descriptions, and `restate sql --help` lists all queryable tables.

**Other changes.** `invocations list` shows the most recently modified invocations first (`--order-by`, `--order` to change) and accepts the same target queries as `cancel`, `pause` and `purge`. `services status` derives active keys from the VQueue lock tables and adds a `paused` count. `example <name>` works without prompting: it downloads into `./<name>` unless `--output-directory` (alias `--out`) is given, reports the example's name, directory and README path with `--json`, exits `4` for an unknown name and `2` for an existing output directory.

**Finding your way around.** `restate search <words>` finds the commands and SQL tables matching a free-text query or a description of what you want to do (for example `restate search pause a stuck invocation`), searching descriptions and flags too and tolerating typos. `restate openapi` prints the Admin API's OpenAPI document as JSON, so you or an agent can discover the Admin API and call it directly, for example with `curl`.

### Google Cloud Storage for Cluster Metadata

The object-store metadata backend accepts `gs://` paths in addition to `s3://`:

```toml
[metadata-client]
type = "object-store"
path = "gs://<bucket>/<prefix>"
```

Credentials are taken from the environment: a service account key via `GOOGLE_SERVICE_ACCOUNT` (file) or `GOOGLE_SERVICE_ACCOUNT_KEY` (JSON contents), otherwise Application Default Credentials (`GOOGLE_APPLICATION_CREDENTIALS` or the `gcloud auth application-default login` file), otherwise the instance metadata server including GKE Workload Identity. Workload identity federation credential files (`"type": "external_account"`) are not supported and fail startup. The `GOOGLE_*` variables apply to every `gs://` client in the process, including snapshots.

The backend passes Restate's Jepsen linearizability tests against a real bucket, but we do not yet have extensive production experience with it. Note that GCS throttles writes to a single object to roughly one per second; sustained bursts of metadata updates to one key, such as heavy node churn, are rate limited where S3 is not.

Thanks to @ismymiddlename for the original contribution ([#5335](https://github.com/restatedev/restate/pull/5335)).

### Service Protocol v7 and Unique Random Seeds by Default

Service protocol v7, introduced as opt-in in v1.7, is now negotiated by default with deployments that support it. It brings direct control over failure handling (pause or fail without retrying), lighter `ctx.run()` acknowledgements, structured suspension events and end-to-end propagation of scope, limit key and idempotency key. Which of these you get depends on your SDK version.

Unique random seeds, which make `ctx.rand()` replay deterministically after restart-as-new, are also enabled by default. Both `experimental-enable-protocol-v7` and `experimental-enable-unique-random-seeds` have been removed.

### OpenAPI Improvements

- **Admin API document works with standard client generators.** The document served at the Admin API's `/openapi` endpoint can now be fed to tools such as openapi-generator. Deployment responses (`GET /deployments`, `GET /deployments/{deployment}`, `PATCH /deployments/{deployment}`) gained a `type` field (`http` or `lambda`). Regenerate clients built from the previous document.
- **Per-service OpenAPI covers all `/restate/` endpoints.** `GET /services/{service}/openapi` now documents the request-response and send endpoints (including their scoped variants with the `x-restate-limit-key` header), and the id- and target-based `attach`, `output` and `status` operations. The old per-handler `attach`/`output` routes (`/restate/workflow/{name}/{key}/...` and `/restate/invocation/{service}/{handler}/{idempotencyKey}/...`) are no longer emitted from the contract.

### Compact Schema Metadata Encoding (Experimental)

Schema metadata (deployments, services, subscriptions, Kafka clusters) can be stored in a substantially more compact encoding, reducing metadata store footprint and the cost of distributing schemas across the cluster. This becomes the default in v1.9.0. To opt in after every node runs v1.8.0:

```toml
experimental-enable-schema-bilrost-encoding = true
```

The option is one-way and takes effect on restart; the stored schema is rewritten the next time it changes (for example on deployment registration). Restate always reads both encodings. Once the new encoding is used you cannot downgrade to older versions than v1.8.0.

### Storage Tuning Options

- **`rocksdb-write-rate-limiter-mode`** controls how `rocksdb-max-write-rate-per-second` is applied. The default `auto-tuned` mode is unchanged: RocksDB lowers the write limit whenever background writes are not using their budget, so after a quiet period the limit sits at 1/20 of the maximum. It then rises by only 5% every 10 seconds, so a sudden burst can be throttled for minutes before the full rate is reached. `fixed` applies the configured maximum immediately with no ramp-up. Set it together with a maximum your storage device can sustain and restart:

  ```toml
  rocksdb-max-write-rate-per-second = "2400 MiB"
  rocksdb-write-rate-limiter-mode = "fixed"
  ```

- **`worker.vqueue-metadata-cache-size`** sets the target number of VQueue metadata entries cached per partition (default `32000`, roughly 9 MiB per partition). Raise it to reduce disk reads for workloads with many VQueues, lower it to save memory. Takes effect on restart.

## Improvements

### Behavioral Changes

- **Less aggressive disk-space reclamation defaults for partition stores.** The previous defaults could trigger substantial background disk I/O after ordinary deletion workloads and increase invocation read latency. The new defaults wait for more deleted data and skip small files, trading slower space reclamation after large deletions for lower steady-state latency. Values you set explicitly are kept. To restore the previous behavior:

  ```toml
  [worker.storage]
  rocksdb-compact-on-deletions-window = 1000
  rocksdb-compact-on-deletions-count = 100
  rocksdb-compact-on-deletions-ratio = 0.25
  rocksdb-compact-on-deletions-min-sst-file-size = "0"
  ```

- **Paced cleanup of completed invocations.** The periodic cleanup controlled by `worker.cleanup-interval` now keeps at most `worker.cleanup-max-in-flight-purges` purges in progress per partition (default `32`). Previously a large backlog of completed invocations was purged as fast as possible, and other requests on the same partitions queued behind the purges; under heavy purge pressure, p99 and p100 latencies dropped from 1.1-2 s to 15-35 ms in our benchmarks. Deployments with high log latency, such as clusters spanning regions, purge fewer invocations per second; if cleanup cannot keep up, completed invocations stay in storage longer than their retention. Watch the new `restate.partition.cleaner_purge_delay.seconds` metric, and if needed raise the limit and restart each node. Higher values purge faster but add more latency to other requests while cleanup runs.

  ```toml
  [worker]
  cleanup-max-in-flight-purges = 64
  ```

- **Automatic cleanup of obsolete VQueue metadata.** Fully empty, unpaused VQueues no longer retain metadata, which bounds partition-store growth for workloads with many short-lived queues. Metadata accumulated by earlier versions can be removed with a one-time migration by setting `experimental-enable-vqueue-obsolete-cleanup = true` after all nodes run v1.7.10 or newer; v1.9 runs it unconditionally. The first start with it enabled may take longer and temporarily increase disk I/O; roll it out gradually across replicas. This shipped in v1.7.10 and is included here for clusters upgrading from earlier v1.7.x releases.

### Observability

- **Override the trace `service.name`.** `OTEL_SERVICE_NAME` and the `service.*` keys in `OTEL_RESOURCE_ATTRIBUTES` now take precedence over Restate's defaults (`service.name=Restate`, `service.namespace=Restate`) for the traces of your invocations, so they can be routed in observability pipelines that key off the service name. Previously user-supplied values were silently overwritten.
- **Correct OpenTelemetry span kinds.** Top-level spans now carry their semantic kind: ingress spans are `Server`, invocation-start spans are `Consumer`, and attempt/end spans are `Internal`. Previously all were exported as `Internal` ([#5097](https://github.com/restatedev/restate/issues/5097)).
- **Unsampled trace context is propagated.** A `traceparent` with sampling flag `00` now reaches your handler with the original trace id instead of the SDK starting a new trace ([#5058](https://github.com/restatedev/restate/issues/5058)).
- **Consistent traces for restart-as-new.** The trace context of an invocation created by restart-as-new is now identical on all replicas of a partition.
- **New metric** `restate.usage.leader_journal_entry_bytes.total` reports journal entry sizes by type, complementing the existing entry counts. It also accounts for entries copied by restart-as-new.
- **New metric** `restate.partition.cleaner_purge_delay.seconds` is a histogram of the delay between a completed invocation's (or its journal's) retention expiry and its actual purge. In steady state its maximum should stay within about twice `worker.cleanup-interval`; a growing value means cleanup is falling behind.
- The metrics `restate.invoker.concurrency_limit`, `restate.invoker.concurrency_slots.acquired` and `restate.invoker.concurrency_slots.released` now track node-wide permits instead of a per-partition quota. `acquired - released` also includes permits held for invocations about to start.

### Stability and Security

- **Ingress rejects spoofed `x-restate-*` headers** (see [Breaking Changes](#ingress-drops-client-supplied-x-restate--headers)).
- **Graceful HTTP/2 shutdown of service connections no longer interrupts unrelated invocations.** When a service endpoint sends a graceful GOAWAY, the connection is retired without cancelling streams already in progress, and the unsent request is retried on another connection.
- **Google credentials for Cloud Run authentication are cached process-wide.** Previously each token mint left a background refresh task behind, which accumulated over time and unboundedly during outages ([#5151](https://github.com/restatedev/restate/issues/5151)).
- **Core dumps exclude the RocksDB block cache**, making dumps of nodes with large caches much smaller and easier to analyze.

## Bug Fixes

- **State changes via the Admin API are applied on all replicas.** With VQueues enabled, `POST /services/{service}/state` (used by `restate state edit|patch|clear`) could be applied on the partition leader but skipped by followers, leaving a follower with stale Virtual Object state once it took over. Only clusters with more than one replica per partition were affected. If you used the state API on such a cluster, re-submit the state of the affected objects after upgrading. A state change missed by a follower before the upgrade may still execute later when that replica becomes leader; to prevent this, an optional one-time cleanup removes all pending state changes and logs each removed one as a warning ([#5416](https://github.com/restatedev/restate/issues/5416)):

  ```toml
  experimental-enable-inconsistent-state-mutation-cleanup = true
  ```

  Enable it only once all nodes run v1.8.0 or newer; partitions that ran the cleanup cannot roll back to older versions.

- **Pending sleeps no longer leak into a later run with the same id.** When a workflow run or an idempotent invocation was killed, completed or purged, its pending sleeps stayed scheduled and could fire into the next run with the same workflow key or idempotency key, waking it up early or failing it with `RT0007 Unexpected variant in async result`. Pending sleeps are now removed. Sleeps already left behind before the upgrade still fire when due ([#5425](https://github.com/restatedev/restate/issues/5425)).
