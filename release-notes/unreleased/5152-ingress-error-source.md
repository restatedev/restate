# Release Notes for Issue #5152: Distinguish ingress errors from invocation errors at the HTTP ingress

## New Feature

### What Changed

HTTP ingress error responses now carry an explicit discriminator that tells whether the error was
generated by the **ingress** (Restate itself) or is the **terminal outcome of the invocation**:

- A new response header `x-restate-error-source` with value `ingress` or `invocation`.
- A new `source` field (same values) in the JSON error body.

Every error response now also carries a JSON body — in particular, load-shedding responses (HTTP
`429`) previously had an empty body and now return `{"message":"...","source":"ingress"}`.

### Why This Matters

Invocation error status codes are user/SDK-controlled: a handler returning a terminal error with
status `503` or `500` was indistinguishable from a transient Restate/ingress failure. This made it
impossible for ingress clients to implement safe automatic retries.

With the new discriminator, clients can tell the two apart unambiguously:

- `x-restate-error-source: invocation` → the durable invocation completed with a terminal failure;
  the status code is user-controlled. Do not automatically retry (the result is durable; reattach is
  a separate decision).
- `x-restate-error-source: ingress`, or the header being absent (e.g. a proxy or an older Restate
  generated the response) → the status code follows normal HTTP semantics; apply standard HTTP retry
  rules.

The header's presence is itself the "this response came from a Restate version that supports the
contract" signal, so clients need no version negotiation — the behaviour degrades gracefully to the
previous status-code-only semantics when the header is absent. The `source` body field mirrors the
header so the signal survives intermediaries that strip unknown headers.

Note: the discriminator is intentionally binary and does not encode submission certainty. Clients
should still disable automatic retries for non-idempotent requests unless they use an idempotency
key.

### How Clients Should Use This

As a reference, below is an example code of how a client should decide to retry or not:

```
if !request.has_idempotency_key:
  // never auto-retry non idempotent requests
  return terminal(response)

// Can read source either from header or body
source = header["x-restate-error-source"] ?? body.source

if source == "invocation":
    // invocation error, never auto-retry
    return terminal(response)
else if status in {408, 425, 429} or (500 <= status <= 599):
    // source is "ingress" or null (a proxy or older server):
    // transient transport/rate-limit hints, or any server (5xx) error
    retry()
else:
    // non-transient 4xx (bad request, not found, ...): not retryable
    return terminal(response)
```

### Impact on Users

- **Existing deployments**: purely additive. Clients that ignore the new header/field are unaffected.
  The HTTP status codes for existing error cases are unchanged.
- **New deployments**: same as above.
- **Migration considerations**: none required. Clients wishing to implement safe retries can start
  consulting `x-restate-error-source` (falling back to the `source` body field).
