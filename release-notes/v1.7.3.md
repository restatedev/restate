# Restate v1.7.3 Release Notes

## Highlights

- **Partition placement control**: Freeze automatic replica-set changes during maintenance, explicitly set placements, or stop all processors for a partition without deleting local stores.
- **More control over manual RocksDB compaction**: Configure bottommost-level compaction, recalculate output levels, and control command timeouts.
- **Improved partition reliability**: Irrecoverable partition processors are now parked and reported as broken instead of retrying indefinitely, and record-cache memory accounting more accurately bounds retained memory.
- **Metrics and query correctness**: Partition metrics no longer leave stale per-partition series, strict Prometheus scrapers can collect Restate metrics again, and SQL queries now correctly sort string-encoded IDs.

## Breaking Changes

### Partition Metrics Aggregated by Node

High-cardinality per-partition gauges for applied LSN lag, snapshot age, and time since the last status update are now reported as per-node quantile gauges. The effective-leader gauge is replaced by a per-node active-leader count, and a new gauge counts partitions whose applied LSN lag is unknown. This prevents stale per-partition series from being left behind when partitions move between nodes.

Dashboards and alerts that query the affected per-partition gauges or their `partition` label must be updated. The bundled Grafana dashboards have already been updated; re-import the latest version to apply the migration automatically.

For custom Prometheus queries:

- Replace `restate_partition_is_effective_leader` with `restate_num_active_partition_leaders`.
- Query `restate_partition_applied_lsn_lag` and `restate_partition_snapshot_age_seconds` as quantile gauges without the `partition` label.
- Replace `restate_partition_time_since_last_status_update` with the quantile gauge `restate_partition_time_since_last_status_update_seconds`.
- Use `restate_partition_num_unknown_applied_lsn_lag` to monitor partitions with unknown lag.

## New Features

### Partition Placement Control

Operators can now freeze automatic replica-set changes for selected partitions during maintenance:

```bash
restatectl partitions placement freeze 0-4 --reason "Rolling restart"
restatectl partitions placement show 0-4
restatectl partitions placement unfreeze 0-4
restatectl partitions placement set 0 --replicas 1,2 --freeze "Pin after migration"
```

The freeze is stored in partition epoch metadata and survives cluster-controller changes. It blocks the cluster controller from creating or retargeting a pending replica set, but allows an existing reconfiguration to complete. Explicit `placement set` operations remain available as operator overrides.

An explicit empty replica set can be used to stop all partition processors for a partition:

```bash
restatectl partitions placement set 0 --freeze --replicas
```

Stopping partition processors does not delete their local partition stores.

Partition administration commands are now grouped under `partitions placement` and `partitions leadership`; the standalone `partitions reconfigure` command has been removed.

### More Control over Manual RocksDB Compaction

`restatectl storage compact` now lets operators control bottommost-level compaction with `--bottommost-level-compaction`. It preserves RocksDB's default behavior, which only rewrites the bottommost level when a compaction filter is configured. Use `force-optimized` to rewrite existing bottommost files after large deletions while avoiding files created during the same compaction.

The `--recalculate-level` flag asks RocksDB to move compacted files to the minimum level capable of holding the resulting data. This is useful when compaction substantially reduces the data size.

The command now waits up to 30 minutes by default, configurable with `--timeout`. Compactions accepted by a node continue in the background if the client times out. Any database, node, or request failure now causes a non-zero exit status after all available results have been printed.

```bash
restatectl storage compact -d partition-store
restatectl storage compact --bottommost-level-compaction force-optimized
restatectl storage compact --recalculate-level --timeout 1h
```

## Improvements

### Behavioral Changes

#### Irrecoverable Partition Processors Are Parked

When a partition processor fails because its local partition store is sealed, the node no longer retries the processor on a backoff. This state means the store's applied LSN is ahead of the log tail, indicating data loss in the log. The node instead parks the processor and reports it as **broken**:

- `restatectl partition list` shows `Broken (ahead-of-log)` in the `STATUS` column.
- `restatectl status` counts broken processors separately, for example `2 (1 broken)` under `FOLLOWERS`.
- The `partition_state` SQL table has a new `broken_reason` column, which is `NULL` while healthy. Its `replay_status` is `NULL` for a broken processor because no replay is in progress.
- The `restate.partition.blocked_flare{reason="ahead_of_log"}` gauge remains raised.

Other blocked states, including version barriers, migration barriers, and missing snapshots, are unchanged and continue retrying because a cluster upgrade or newly published snapshot can resolve them.

A sealed store cannot be repaired by retrying: the local data must be discarded and replaced from a snapshot. A parked processor stays down until an operator intervenes, the node restarts, or the node leaves the partition's replica set. Healthy deployments require no action. Older `restatectl` builds ignore the new field and render a broken processor as a follower that never becomes active.

### Observability

#### Invocation-Client Retry Backoff and Metrics

HTTP ingress requests now retry retryable invocation-client failures with exponential backoff, starting at 50 milliseconds and capped at one second between attempts. Previously, retries used a fixed 50-millisecond delay. This reduces repeated traffic to stale partition leaders during leadership changes.

A new `restate.invocation_client.requests.total` counter records partition-processor RPC attempts by `partition_id` and `status`. Status values distinguish completed requests from routing, availability, overload, protocol, internal, and shutdown errors.

The `status` label on `restate.ingress.requests.total` now distinguishes `completed`, `request_error`, `invocation_error`, and `ingress_error` outcomes. Ingress request duration is also recorded for unsuccessful requests.

Existing and new deployments adopt the retry behavior automatically. Prometheus queries that use `status="completed"` to calculate the total processed ingress request rate should include `request_error`, `invocation_error`, and `ingress_error` as appropriate.

## Bug Fixes

### Valid Prometheus Exposition for Shuffle Metrics

The `restate_partition_shuffle_inflight_count` summary metric introduced in v1.7 is replaced by the `restate_partition_shuffle_inflight` gauge. The previous underlying metric name ended in `.count`, which collided with the Prometheus exporter's summary suffix handling and produced an invalid sample line without a `quantile` label. Strict Prometheus scrapers, such as Vector's `prometheus_scrape` source, rejected the entire scrape payload when they encountered this malformed line.

The `restate_partition_shuffle_message_count` counter is also renamed to `restate_partition_shuffle_message_total` to follow the naming convention for counters.

Deployments using strict Prometheus text-format parsers can collect all Restate metrics again. The in-flight metric is now exposed as a gauge without the summary's `_sum`, `_count`, and `{quantile=...}` series.

Update dashboard and alert queries as follows:

- Replace `restate_partition_shuffle_inflight_count` with `restate_partition_shuffle_inflight`.
- Replace `restate_partition_shuffle_message_count` with `restate_partition_shuffle_message_total`.

_Related: #5034_

### Bounded Record-Cache Retained Memory

The record cache now copies raw record bodies when admitting them to the cache. This prevents a small cached body that is a slice of a larger buffer from retaining the full backing allocation.

The record cache's memory budget now more accurately bounds the memory retained for raw records, reducing the risk of unexpected memory growth and out-of-memory failures under sustained log traffic. Existing and new deployments receive this protection automatically; no configuration or application changes are required.

### Correct SQL Ordering by ID

The SQL tables `sys_invocation_status`, `sys_invocation_state`, `sys_journal`, `sys_journal_events`, `sys_inbox`, `sys_vqueue_meta`, and `sys_scheduler` no longer declare the `id` column as pre-sorted to the query engine. The underlying storage orders rows by the binary key encoding, which does not match the lexicographic order of the string-encoded `id` column. DataFusion previously trusted the declared ordering and could skip sorting, returning rows in storage order instead of the requested order. Queries that group or deduplicate on `(partition_key, id)` relied on the same incorrect ordering through sort-based aggregation.

The `partition_key` column remains declared as sorted because its numeric order matches the storage order. Queries ordering by `id` now include an explicit sort step and return correctly ordered rows. Common query forms, including the default ascending and descending orderings, the CLI's invocation listing, and the `sys_invocation` view join, were already planned with a sort and are unaffected. No configuration or code changes are required.
