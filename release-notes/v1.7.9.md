# Restate v1.7.9 Release Notes

## Highlights

- **Non-blocking invocation status**: Poll an invocation's coarse-grained lifecycle stage through new HTTP ingress endpoints without waiting for its output.
- **Stronger storage reliability**: RocksDB iterator failures are now propagated, and partition-store direct writes use consistent crash-recovery semantics.
- **More reliable service execution**: AWS Lambda connections detect silent failures sooner, while VQueue storage refills now run synchronously by default.

## New Features

### Retrieve Invocation Status through the HTTP Ingress

The HTTP ingress now provides non-blocking endpoints that immediately return an invocation's current lifecycle stage:

- `GET /restate/invocation/{invocation_id}/status`
- `GET /restate/invocation/{service}/{handler}/{idempotency_id}/status`
- `GET /restate/invocation/{service}/{key}/{handler}/{idempotency_id}/status`
- `GET /restate/workflow/{name}/{key}/status`
- `GET /restate/status/{invocation_id}`
- `POST /restate/status` with a body identifying the invocation target

The JSON response contains a coarse-grained `stage` of `created`, `started`, or `completed`. When an invocation completes with a failure, it also contains the terminal `error`:

```json
{
  "stage": "created",
  "error": null
}
```

The response includes the resolved invocation ID in the `x-restate-id` header. Unknown invocations return `404 Not Found`. Existing ingress routes are unchanged, and no migration is required.

_Related: [#5178](https://github.com/restatedev/restate/pull/5178)_

## Behavioral Changes

### Synchronous VQueue Refills by Default

VQueue storage refills now run synchronously by default. This avoids scheduling refill reads on Tokio's blocking thread pool. Existing deployments adopt the new behavior automatically after upgrading.

The previous asynchronous refill path remains available through this experimental option:

```toml
[common]
experimental-enable-vqueues-async-refill = true
```

No configuration changes are required unless you want to retain asynchronous refills.

_Related: [commit 72ddd43](https://github.com/restatedev/restate/commit/72ddd4398c0efab2981b36ef9a13987d6f3d353d)_

### Defer Orphaned Journal Index Cleanup

Restate v1.7.9 disables the one-time cleanup of historical orphaned journal completion-ID index entries. Normal journal deletion continues to remove its completion-ID index entries.

The existing completion marker cannot account for entries created after rolling back to Restate 1.6. If cleanup completed before a rollback, Restate 1.6 could create new orphaned entries and a subsequent Restate 1.7 startup would skip cleanup because the marker was already present.

Cleanup is deferred until Restate 1.8, where it can safely account for this rollback scenario. Restate 1.7.9 does not perform the historical startup scan, and no configuration or user action is required. Upgrade to Restate 1.8 once its revised cleanup is available to reclaim historical orphaned entries.

_Related: [#5238](https://github.com/restatedev/restate/issues/5238), [#5283](https://github.com/restatedev/restate/pull/5283)_

## Improvements

### Detect Stalled AWS Lambda Connections

Restate now enables HTTP/2 keep-alive pings for AWS Lambda invocations. The existing `worker.invoker.http2-keep-alive-interval` and `worker.invoker.http2-keep-alive-timeout` options now also apply to Lambda, retaining their defaults of `40s` and `20s`.

With the defaults, Restate detects a silently dropped Lambda connection within about one minute instead of waiting for the kernel's TCP retransmission timeout, which can take around 15 minutes. Idle connections are also pinged so that dead pooled connections can be discarded before another invocation uses them.

Set `worker.invoker.http2-keep-alive-interval` to `0` to disable pings. The pings require HTTP/2; endpoint overrides that negotiate HTTP/1.1 retain the previous behavior. AWS credential providers, STS, and proxy handling are unchanged. No migration is required.

_Related: [#5255](https://github.com/restatedev/restate/pull/5255)_

### Restate UI 1.0.25

The bundled Restate UI is updated from **v1.0.22** to **v1.0.25**, incorporating the fixes and improvements from the v1.0.23, v1.0.24, and v1.0.25 UI releases.

No configuration or migration changes are required.

## Bug Fixes

### Propagate RocksDB Iterator Errors

Restate now distinguishes RocksDB iterator failures from clean iterator exhaustion and propagates those errors instead of returning empty or partial results. The fix covers partition-store scans, journal-index consumers, metadata-server Raft index discovery, and log-server local-tail recovery.

This prevents storage read failures from being mistaken for missing data or the end of a scan. No configuration or migration changes are required.

_Related: [#5248](https://github.com/restatedev/restate/issues/5248), [commit a44f81a](https://github.com/restatedev/restate/commit/a44f81aee4364910132c4b4423a36ef4de1f533c)_

### Consistent Partition-store Crash Recovery

Partition-store direct puts and deletes now disable the RocksDB write-ahead log, matching transaction and migration writes. Partition-store state is recovered from Bifrost, so mixing WAL-enabled direct writes with WAL-disabled writes could allow later metadata to survive a crash while preceding data changes were lost.

All recoverable partition-store writes now use consistent crash-recovery semantics, preserving the ordering assumptions used by storage migrations. No configuration or migration changes are required.

_Related: [commit e7ba3a8](https://github.com/restatedev/restate/commit/e7ba3a88f82df5317f7cfe8633fa710647cd117b)_
